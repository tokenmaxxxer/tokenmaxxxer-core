# Implementation record — issue-109

## Why

Phase 2, delivering the approved phase-1 proposal
`docs/issue-109/proposals/2026-08-04-align-issue-drafting-with-orchestrator-skill-invocation.md`.
Issue #109: on-the-record #258 / PR #259 amended
`on-the-record/commands/run.md` step 1 so the orchestrator, before drafting
an issue, judges per-request whether any of the user's available skills
apply, invokes applicable ones through the real `Skill` mechanism, and
folds each invoked skill's procedural demands into the issue draft's
requirements/acceptance-criteria text, while role sessions stay
skill-isolated. This repo's `core/contract/role-handoff-contract.md` §9
had its own issue-drafting description and had drifted out of alignment
with `run.md`. This record delivers exactly the approved proposal's
`## What will be done`.

## What was done

1. `core/contract/role-handoff-contract.md` §9 (`` `subject` is the
   issue ``) — inserted a new subsection, "Skill assessment before an
   issue is filed," immediately after the existing paragraph ending
   "...This holds regardless of whether the repo has a remote configured."
   and before §10, per the proposal's exact placement instruction. The
   subsection restates, in the contract's third-person descriptive voice
   (matching §9's and its neighbors' register, not `run.md`'s imperative
   Korean step text), the four load-bearing points named by the proposal:
   per-request orchestrator judgment over available skills (not a fixed
   mapping lookup), invocation through the real `Skill` tool mechanism
   (reading-and-paraphrasing does not satisfy it), folding the invoked
   skill's procedural demands into the issue's requirements/
   acceptance-criteria text (the skill call itself produces no artifact),
   and role-session skill-isolation (no skill injected into a role
   session; only the issue's own text, already carrying any folded-in
   demands, reaches the role). The subsection closes by citing
   on-the-record #258 / PR #259 as the source decision.
2. No other section of the contract was touched; no rulebook, `spawn.py`,
   or skill file was changed, per the issue's own out-of-scope list and
   the proposal's `## Out of scope`.

Doc-placement ladder: this change is itself the contract-doc edit the
proposal specified — no further decision or document is generated by
this delivery, so no separate decision record is needed.
